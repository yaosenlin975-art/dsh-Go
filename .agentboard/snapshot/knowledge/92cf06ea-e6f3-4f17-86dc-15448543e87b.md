# Android 后台跑 agent 的运行契约

## 结论
本机引擎是 App 进程的 `ProcessBuilder` 子进程（`DshProcess`），所以「后台一轮能不能跑完」只取决于两件事：App 进程不被回收、引擎的请求通路不断。二者要分别保：

1. **进程**：`DshService`（`specialUse` 前台服务）+ `PARTIAL_WAKE_LOCK`，且 `onStartCommand` 返回 `START_STICKY`。缺 FGS 或唤醒锁时，息屏后进程会被 Doze/厂商策略冻结或回收；`START_STICKY` 让系统回收服务后重建（null intent 走 `else` 分支重启引擎），主动停止走 `stopSelf` 不会被重建，两者不能混。引擎进程退出由 `RuntimeController` 归类为「killed from outside」并自动重启，用户看到的是「已中断 · 引擎重启过」。
2. **网络**：`PARTIAL_WAKE_LOCK` 只保证 CPU 运行，**不保证 Wi-Fi 射频**。息屏后射频可进入省电/关闭，长连接上的模型请求超时失败；这是「电池优化已豁免仍会被打断」的常见原因——豁免只影响 Doze，不影响射频休眠。对应的锁是 `WifiLock`（`WIFI_MODE_FULL_HIGH_PERF`），需与唤醒锁同生命周期持有/释放；获取失败必须留 `[dsh-app] wifi lock unavailable: <原因>` 日志，不能 `runCatching` 静默吞掉（否则断连现场无迹可查）。
3. **提示策略**：厂商「后台联网 / 无限制数据」开关与电池优化豁免是两套设置。`BackgroundNetPolicy.onReturn` 与 `introDue` 都不以豁免状态做门禁——已开白名单的手机同样需要被告知这些开关在哪。

## 约束与坑
- 电池优化豁免（`isIgnoringBatteryOptimizations`）不等于厂商的「允许后台高耗电 / 自启动 / 后台联网」开关；后者无 API 可读，只能由用户自述（`AccessItem.vendorBackground` 因此返回 null）。
- 厂商断网与 Doze 是两回事：`NetworkAccess` 记录的 `onBlockedStatusChanged` 才是系统层面的实证，判断「后台被打断」优先看它，而不是看豁免状态。
- 客户端不会因断线取消 turn：`session/cancel` 只在用户点停止时发送；`chat_state` 的 30s 静默/重订阅只作用于远程主机。所以后台中断的归因方向是「进程/网络」，不是「客户端主动取消」。
- 引擎侧对传输失败有 `LlmRetryEvent(TRANSPORT)` 重试；重试耗尽才结束 turn，因此症状表现为「跑了一会儿被打断」而不是立刻报错。
- `START_STICKY` 与 `stopSelf` 的关系要成对检查：若停止路径没走 `stopSelf`，服务会被系统反复拉起；若重建路径依赖 intent，则 null intent 必须落进可恢复分支。

## 验证方式
- 真机：前台发起长 turn → 息屏 + 切后台 → 观察是否出现 TRANSPORT 重试/中断；导出诊断包核对 `networkBlockedAt` 与引擎退出码，用于区分「网络被断」与「进程被杀」。
- 日志判据：`[dsh-app] background policy: …`（豁免/流量节省/通知三态）、`[dsh-app] the system blocked this app's network (app in background)`、`[dsh-app] killed from outside; restarting in Ns`、`[dsh-app] wifi lock unavailable: …`。
- 静态：`WifiLock|WIFI_MODE` 与 `START_STICKY` 可用全仓检索判定；后台提示逻辑用 `app/test/notify/background_net_test.dart` 复算；引导页文案改动会动 `background_guide_vivo` golden，需 `flutter test --update-goldens test/settings/background_guide_test.dart`。
