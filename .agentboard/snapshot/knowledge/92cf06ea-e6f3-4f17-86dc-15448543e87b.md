# Android 后台跑 agent 的运行契约

## 结论
本机引擎是 App 进程的 `ProcessBuilder` 子进程（`DshProcess`），所以「后台一轮能不能跑完」只取决于两件事：App 进程不被回收、引擎的请求通路不断。二者要分别保：

1. **进程**：`DshService`（`specialUse` 前台服务）+ `PARTIAL_WAKE_LOCK`。缺 FGS 或唤醒锁时，息屏后进程会被 Doze/厂商策略冻结或回收；引擎退出由 `RuntimeController` 归类为「killed from outside」并自动重启，用户看到的是「已中断 · 引擎重启过」。
2. **网络**：`PARTIAL_WAKE_LOCK` 只保证 CPU 运行，**不保证 Wi-Fi 射频**。息屏后射频可进入省电/关闭，长连接上的模型请求超时失败；这是「电池优化已豁免仍会被打断」的常见原因——豁免只影响 Doze，不影响射频休眠。对应的锁是 `WifiLock`（`WIFI_MODE_FULL_HIGH_PERF`），需与唤醒锁同生命周期持有/释放。

## 约束与坑
- 电池优化豁免（`isIgnoringBatteryOptimizations`）不等于厂商的「允许后台高耗电 / 自启动」开关；后者无 API 可读，只能由用户自述（`AccessItem.vendorBackground` 因此返回 null）。
- 厂商断网与 Doze 是两回事：`NetworkAccess` 记录的 `onBlockedStatusChanged` 才是系统层面的实证，判断「后台被打断」优先看它，而不是看豁免状态。
- 客户端不会因断线取消 turn：`session/cancel` 只在用户点停止时发送；`chat_state` 的 30s 静默/重订阅只作用于远程主机。所以后台中断的归因方向是「进程/网络」，不是「客户端主动取消」。
- 引擎侧对传输失败有 `LlmRetryEvent(TRANSPORT)` 重试；重试耗尽才结束 turn，因此症状表现为「跑了一会儿被打断」而不是立刻报错。

## 验证方式
- 真机：前台发起长 turn → 息屏 + 切后台 → 观察是否出现 TRANSPORT 重试/中断；导出诊断包核对 `networkBlockedAt` 与引擎退出码，用于区分「网络被断」与「进程被杀」。
- 静态：`WifiLock` 缺失可用全仓检索 `WifiLock|WIFI_MODE` 判定；后台提示逻辑用 `app/test/notify/background_net_test.dart` 复算。
