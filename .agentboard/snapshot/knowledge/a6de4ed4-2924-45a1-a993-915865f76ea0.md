# 流式 Markdown 预处理的逐行/逐字符工作

## 契约

- 聊天流式输出由 ChatController._schedule() 做 32ms 合并发布；每次发布都会对当前回复全文跑一遍源码预处理（流式修复、公式归一、表格补空行/加粗表头）。
- 因此「每行一次」「每字符一次」的函数，实际会被放大为「行数 × 每秒 31 次」。

## 坑

- 在这些函数体内直接写 new RegExp 字面量：每次调用都重新解析模式串。含代码块/公式/表格的长回复流式期间可达每秒上万次构造，白白吃掉预处理预算（文档记录预处理约 10ms/次）。
- 典型位置：_Fence.closedBy（围栏内每行）、_readsAsPrices（每个行内美元公式候选 2 个）、_unquoted/_quotePrefix/_boldRow（按行）、_isPunct（每个 ASCII 字符）、_cells/_unfinishedTableAt/_InlineScan.cut。

## 做法

- 会被逐行/逐字符调用的正则一律提升为文件级或类级 final；模式串逐字保持原样，避免行为漂移。
- 判定标准：函数位于 prepareSource/_prepareRevealed/repairStreamingMarkdown 的调用链上，或按行/按字符循环调用。

## 验证

- 有 Flutter SDK 的环境执行 (cd app && flutter analyze && flutter test)；本机无 flutter/dart SDK，无法执行。
- 设备帧率/耗电需真机测；发布节流与预处理路径见 docs/design/rendering.md 的「已知限制」。

## 复制开销（同一路径，补）

- 发布节流 32ms 仍会把整段回复变成 String：_Draft.items 在单 text 块时用聚合 StringBuffer 写一遍再 toString，等于每次复制 2L 字符（62L 字符/秒；L=100KB 约 12MB/s 短命分配）。单块快速路径直接 block.text.toString() 可降到 1 次。
- normalizeMath 在回复含美元符号时每次发布全文扫描：原实现逐字符 writeCharCode（每次发布 n 次调用）、行首对每行 materialize 一次 substring 只为判定围栏、结尾再全文 toString。可先看首非空白/引用字符是否为反引号或波浪号再决定是否构造该行；普通字符段整段 substring 写入。
- 逐 delta 字符串 += 是 O(n²) 累积（companion 轻聊、tavern 草稿）；修法是用 StringBuffer 累积 + 沿用 32ms 合并发布，不要每个 token 直接 setState。
